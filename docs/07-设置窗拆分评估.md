# SettingsWindowController 拆分评估

> 版本 v1.0 ｜ 2026-10-26 ｜ 评估对象：`mac/Sources/SettingsWindowController.swift`，7,717 行
> 结论：**现在不做整体拆分。先删商业化，再加页面注册表，老页面改到才迁。**

## 一、先问对问题

要拆的理由通常有四条：文件太大、改起来怕、没法测、将来要加页面。

第一条是表象。真正的成本是**一个对象里同时装着 170 个方法和 71 个可变字段**，读者要在脑子里同时维持这些状态。文件行数只是它的度量。

拆成 8 个文件而共享同一批字段，行数好看了，读者负担没变。这是判断一切拆分方案的标准。

## 二、测量结果

| 区段 | 行数 | 方法数 |
|---|---|---|
| 壳与侧栏（生命周期、侧栏、滚动容器、页面切换） | 1,138 | 28 |
| 首页 | 390 | 13 |
| **商业化（试用/会员/升级弹窗/价格卡/激活）** | **889** | **28** |
| 配置健康 | 197 | 5 |
| 探索 | 103 | 3 |
| 设置 | 380 | 6 |
| 模型 | 1,381 | 34 |
| 历史 | 796 | 13 |
| 词库 | 495 | 9 |
| 关于 | 64 | 1 |
| 通用 helper（卡片、标签、分隔线、按钮工厂） | 843 | 30 |
| **合计** | **7,717** | **170** |

其他耦合指标：

| 指标 | 数值 |
|---|---|
| 类内 `private` 存储属性 | 71 |
| `@objc` 方法（按钮 target-action 依赖） | 81 |
| `NotificationCenter` 监听 | 15 |
| 区段外的工单注释（隐性行为） | 7 处 |
| 带日期的历史决策注释 | 9 处 |

**第一个发现**：商业化占 889 行、28 个方法，且是耦合最重的一块（会员卡、升级弹窗、价格表、激活流程）。这部分在 P0 就要删。删完文件降到约 6,828 行，不拆也少了 12%。

**第二个发现**：模型页 1,381 行、34 个方法，是最大的业务页。它同时是 P0 必改页（要删会员区），所以它是拆分的最佳试点，不是包袱。

## 三、拆开能得到什么

| 声称的收益 | 是否成立 | 说明 |
|---|---|---|
| 单次改动要读的行数下降 | **成立** | 从 7,717 行降到单页 100~1,400 行 |
| 作用域里的方法数下降 | **成立** | 从 170 个降到 1~34 个 |
| 新页面有独立落点 | **成立** | 从"往 7 千行文件里加"变成"新建一个文件" |
| 减少合并冲突 | 不成立（单人） | 只有第二个人加入才成立 |
| 可单元测试 | **不成立** | AppKit 视图没有 host app 就测不了。拆文件不产生测试，把逻辑挪进 Core 才产生测试 |
| 编译更快 | 不成立 | Swift 增量编译对单文件拆分的收益可忽略 |

三条真收益，三条幻觉。幻觉里最容易误导的是"拆开就能测"。

## 四、拆开要付出什么

| 风险 | 概率 | 影响 | 具体表现 |
|---|---|---|---|
| `@objc` selector 断链 | 高 | 中 | 81 个 selector，按钮点了没反应，不崩溃、不报错、无测试会发现 |
| 封装被迫放开 | 高 | 中 | 换文件后 `private` 必须改 `internal`，71 个字段 + ~150 个方法对整个模块可见 |
| 布局约束跨方法 | 中 | 高 | `makeCard()` 只建容器，约束由调用方加。换类后容器/嵌入关系要重接，容易错位或约束冲突 |
| 生命周期时序 | 中 | 高 | `setupShell → rebuildSidebar → selectPage → buildScroll` 有隐含顺序，拆成对象后时序变化会产生"首屏空白"这类偶发问题 |
| 无回归网 | 高 | 高 | App 层零自动化测试，所有验证靠手工点 8 个页面 |
| 隐性规则丢失 | 中 | 中 | 7 处工单注释、9 处日期注释记录着"为什么这样写"，机械搬迁最容易丢 |

## 五、三种拆法

| 方案 | 做法 | 成本 | 风险 | 收益 |
|---|---|---|---|---|
| **L1 机械分文件** | 同一个类，方法搬到多个 `extension` 文件 | 2 人日 + 2 人日回归 | 中（封装全开） | 只有导航收益，状态仍在同一对象 |
| **L2 页面对象化** | `SettingsPage` 协议 + `PageContext` + 注册表，每页一个类 | 6~7 人日（8 页）+ 2 人日回归 | 中高（时序与约束） | 真收益三条全拿到，且新页面按新范式写 |
| **L3 设计系统 + 组件化** | 在 L2 之上抽卡片/列表/表单组件 | 再 +4~6 人日 | 中 | 一致性提升，新页面更快 |

**不推荐 L1**。它付出封装代价，只换来"文件变小"，恰好是唯一不重要的那条。

## 六、回本计算

按单人开发、每次页面级改动节省 0.1~0.2 人日的阅读与定位时间算：

- L2 成本 8~9 人日
- 回本需要 **45~90 次页面级改动**

一年内如果只加 3~5 个页面和少量调整，纯效率上不回本。

所以要不要拆，不该看效率，只看两个信号：**要加的新页面 ≥3 个**，或者**要进第二个人**。两个都还没发生。

## 七、建议（v1.0 初版，已被第十节修订）

**第一步（P0，必做）**：删商业化与反馈页。889 + 42 行，28 个方法。这是纯减法，风险低，收益立竿见影。

**第二步（P0，建议做，+1 人日）**：加页面注册表。不是拆分类，只把"页面怎么被发现"从三处 switch 改成一个协议加一张注册表。

```swift
protocol SettingsPage {
    var id: SettingsPageID { get }
    var title: String { get }
    func build(context: PageContext, into stack: NSStackView)
}
```

新页面（待办页）第一个按这个范式写，作为样板。老页面继续走原 switch，两者共存，不冲突。

**第三步（按需）**：老页面改到才迁。模型页和首页在 P0 就要改，顺手迁掉，作为 L2 的两个试点。其余页面等真被改到时再说。

这样做的效果：新代码永远落在新文件里，老文件只减不增，重构风险被摊薄到每次改动里，没有"大爆炸"窗口。

## 八、什么时候重新评估

满足任一条件就启动 L2 全量迁移：

1. 页面数 ≥ 10（当前 8；一期删反馈、加待办后仍是 8）
2. 第二个人开始改这个文件
3. 文件行数 > 10,000
4. 需要在同一页面做三次以上连续改动

## 九、本评估用到的判断原则

- **Attack the Premise**：把"文件大所以难维护"当作待检验的前提。测下来真正的成本是 71 个字段与 170 个方法共存，不是行数。这改变了结论：拆文件不等于拆耦合。
- **Minimize Reader Load**：同时看"层的数量"和"要记住的状态"。L1 只减少行数，不减少状态，还会因为 `internal` 放开而增加可访问状态，属于负收益。
- **Subtract Before You Add**：先删 889 行商业化，再谈拆分。减法后的基础上判断，比在 7,717 行上判断更准。
- **Laziness Protocol**：用注册表加"改到才迁"替代全量重写，是解决同一问题的最小改动。

## 十、修订（2026-10-27）

前提变了，结论跟着改。

新事实：单人开发、全部由 AI 执行、没有工期压力。

原建议"改到才迁"的前提是"拆分成本高、验证靠手工"。这两条在新前提下都松动了：

1. 成本下降。8~9 人日的机械搬迁，AI 执行约 1~2 个工作日。
2. 风险可部分对冲。selector 断链是拆分最大的隐患，现在有静态检查兜底：基线 116 个本地 selector、0 孤儿、8 个页面全有分支，每一步搬完重跑即可。
3. 文件只会继续长大。一期就要加待办页和清单管理，二期还有会员页。晚拆意味着在更大的文件上拆。

**修订后的建议**：P0 内一次性完成 L2，不再等"改到才迁"。

保留的约束：

- 先删商业化，再拆。在 6,828 行上拆，比在 7,717 行上拆少 889 行干扰。
- 一次只搬一页，单独 commit，每步跑 `tools/check_app_invariants.py`，退出码必须为 0。
- 不合并"搬家"与"改逻辑"。搬迁 commit 里只允许出现位置变化。
- 顺序：组件 → 关于/探索（最小页验证模板）→ 设置/词库 → 历史 → 模型 → 首页 → 壳收尾。

原"改到才迁"降级为备选：如果一次性搬迁中途发现某页耦合异常，允许暂停，其余页面按新范式继续，旧页保留到下次。

详见 `docs/06-开发方案.md` §3.3 与 §9（P0.5）。

> 本评估为技术决策参考，最终以实际改动频率与团队规模判断。
