# 空白处长按调研 · 手势定案 · 本地提醒方案

> 版本 v0.1 ｜ 2026-10-26 ｜ 承接《02-授权路径与 Typetodo 功能方案》
> 回答：「空白处长按现在到底做了什么？为什么没弹出输入 UI？」以及「本地提醒怎么做」

---

## 一、调研结论（先给答案）

**这个操作上游已经实现了，而且默认开启——它就是「随时问 AI」。**

| 你的观察 | 实际原因 |
|---|---|
| 在空白处长按，麦克风被唤起 | ✅ 正常。`onStartAsk` 立刻调用 `startRecording`，录音真的开始了 |
| 但没弹出输入框/胶囊 | ✅ 设计如此。**要等判定出「用户开口说话」，才弹胶囊**（`feedAskSpeechDetector` 里那句注释写得很清楚：*"开口确认了才弹胶囊"*） |
| 松手后什么都没发生 | ✅ 也是设计。录音 <1 秒、或全程没响过阈值线 → 判定为误触，`discardAskRecording()` 静默丢弃，不提示、不识别 |
| 就算正常说话，文字也没进输入框 | ✅ 它**从不投递文字**。答案显示在屏幕右上角的「回答面板」里，可追问、可固定 |

一句话：**空白处长按 = 问 AI，结果进回答面板，不进光标。** 你在设置 → 探索页能看到两张卡片：「鼠标长按说话」和「长按问 AI」，各有独立开关，默认都开。

## 二、代码级证据

### 2.1 判定链

```
左键按下 0.12s 预热（Chromium 类 App 需要）→ 0.45s 判定长按
        ↓
TextInputLocator.classify(点, pid?, bundleID?)
        ├─ .editable / .editableNearby  →  长按说话（听写）
        ├─ .askable                     →  长按问 AI
        ├─ .notEditable                 →  不触发（按钮/链接/图片/列表行/视频画面）
        └─ .unknown                     →  不触发（读不到证据：桌面、部分 App）
```

关键文件：`MouseHoldToTalkManager.swift:564-620`（`decide` / `applyVerdict`）、`TextInputLocator.swift:8-30`（`TextInputVerdict`）。

`askable` 的判定不是"空白"这么简单：命中的元素**不可点击**（不在 `interactiveRoles` 里）、不在视频画面上、不是被遮罩挡住的大容器，才归为 `askable`。所以：

- 网页正文、文档空白、聊天消息区 → `askable` → 问 AI ✅
- 按钮、链接、图片、列表行 → `notEditable` → 什么都不发生
- **桌面 / Finder 空当 → 多半是 `unknown` → 也不触发**（这点容易被误认为"失灵"）

### 2.2 时间线与常量

| 常量 | 值 | 含义 |
|---|---|---|
| `holdThreshold` | 0.45s | 按住多久算长按（普通点击 0.1~0.2s） |
| `warmUpDelay` | 0.12s | 按下后预热 AX 查询 |
| `moveTolerance` | 6pt | 超过即视为拖拽，不触发 |
| `askPendingMoveTolerance` | 20pt | 问 AI 已开录但未判出开口时，拖动 = 在 App 里选字，静默撤销 |
| `AskSpeechDetector.ratio` | 1.8× | 相对本次录音最安静帧的倍数 |
| `framesNeeded` | 3 帧 | 连续过线帧数，单帧键盘声攒不够 |

`AskSpeechDetector` 用的是**自适应阈值**（拿本次录音最安静的一帧当基准），不是固定音量线——因为 MacBook 内置麦安静时 0.03~0.05，外置麦开麦就有 0.11~0.13，固定线必然误判。这段注释里有 2026-09 的真机实测数据，是很扎实的设计。

### 2.3 状态机（问 AI 的完整链路）

```
按下 → 判定 .askable → onStartAsk
   ├─ voiceQuestionMode = true, askAwaitingSpeech = true
   ├─ startRecording()（此时只有菜单栏图标变成 VP●，屏幕无 UI）
   ├─ 未开口就拖动 >20pt → 当作选字，静默撤销
   └─ 判出开口 → 弹胶囊 + 接管按键（askSpeechDetected）
松手
   ├─ 未判出开口 且 (<1s 或 从未过线) → 丢弃
   ├─ 未判出开口 但 (≥1s 且 曾过线)  → 照常识别（离麦远时说话攒不够帧）
   └─ 已判出开口 → 识别 → askAI → 回答面板（右上角）
```

## 三、手势定案：原版不动，用修饰键另开一条

**用户已决策：保住原版行为，空白处长按仍然是「问 AI」，不改。**

那么待办入口只能另起一条。候选是「修饰键 + 左键长按」，逐个排查系统与常见 App 的占用情况：

| 组合 | 已被谁占用 | 长按可行性 | 结论 |
|---|---|---|---|
| **⌘ + 左键** | Finder 多选、浏览器 ⌘-点开新标签、Xcode/VS Code/JetBrains 跳转定义、终端打开链接 | **高**（占用的都是"单击/松手触发"，长按不冲突） | ✅ 推荐 |
| ⌥ + 左键 | VS Code 块选择（⌥+拖拽）、Figma 复制拖拽 | 中高 | 备选 |
| ⇧ + 左键 | 文本扩展选区（按住 ⇧ 点 = 选中到该点） | 低 | ❌ 按住就改选区 |
| ⌃ + 左键 | **系统级等于右键**（Control-click） | 不可用 | ❌ 直接弹菜单 |
| 右键长按 | 右键菜单在 `rightMouseDown` 即弹出 | 低 | ❌ 需吞事件 + 合成，菜单失真 |
| 中键 / 侧键长按 | 无 | 高 | ⚠️ 触控板没有中键，覆盖率低 |

### 定案

```
输入框 + 长按            → 听写（原版，不变）
空白处 + 长按            → 问 AI（原版，不变）
⌘ + 空白处长按           → 记待办（新增）
⌘ + 输入框长按           → 不启用（避免与"跳转定义 / 多选"打架）
⌥Space / 菜单栏          → 记待办（兜底入口）
右键长按                 → 不做（冲突大、收益小）
```

### 为什么 ⌘ 可行，而右键不行

区别在**触发时机**：

- 右键菜单在 `rightMouseDown` **那一刻**就弹出，我们要长按就必须先吞掉事件，再补发合成事件——必然失真。
- ⌘+左键的副作用（新标签、跳转定义、多选）几乎都在 **mouseUp / click 时**发生。我们只在"按住超过阈值"后才接管，**短按完全不干预**，所以绝大多数场景不受影响。

### 四条必须遵守的约束

1. **只在 `.askable`（非可点击区域）生效**。链接、按钮、图片、列表行一律不触发——否则长按松手会在浏览器里多开一个标签页。
2. **输入框内不启用**。代码编辑器整块是 `AXTextArea`，⌘-点等于"跳转定义"，长按容易误触。
3. **阈值放宽到 0.55~0.6 秒**（普通长按是 0.45s）。⌘ 手势没有位置线索，稍长一点更稳。
4. **必须先按 ⌘ 再按鼠标**。判定在 `mouseDown` 的 `event.modifierFlags` 上取；同时监听 `flagsChanged`，支持"按住鼠标后再补按 ⌘"也能进入（可选增强）。

### 反馈设计（这个手势没有视觉预期，必须补）

- 按下 ⌘ 时，菜单栏图标变成待办态（如 `✓` 轮廓）——告诉用户"修饰键已被识别"。
- 达到阈值开始录音时，播一次开始音（复用上游 `CueSound`，它已有三种音效与开关）。
- 松手后：胶囊变成"已添加：明天 15:00 交周报"，5 秒内可撤销。

### `.unknown` 的处理

`.unknown`（桌面 / Finder / 读不到结构的 App）目前完全不触发。对听写是合理的（不知道焦点在哪，粘错地方很糟），但**记待办风险低得多**——最坏是多一条，还能撤销。建议：**⌘ 记待办模式下把 `.unknown` 放行为 `askable`**，让"在桌面按住 ⌘+鼠标记一条"也能用。这是 typetodo 相对上游的一个小改进。

## 四、本地提醒方案（一期）

上游**完全没有**通知相关代码（`grep UserNotifications` 零命中），这套要从零写，但也意味着没有历史包袱。

### 4.1 技术选型

`UserNotifications.framework`（`UNUserNotificationCenter`），系统级调度：

- App 不运行时照样投递（通知已排进系统，不是我们的进程在跑）
- 自动遵守专注模式 / 勿扰
- 支持通知上的按钮（完成 / 延后），不用打开 App

### 4.2 权限与降级

| 环节 | 做法 |
|---|---|
| 申请时机 | **不首启就弹**。第一次创建「带时间的待办」时才申请，用户能理解为什么 |
| 被拒绝 | 不阻断功能。降级为：菜单栏角标 + 清单内红点 + 设置页一条"去系统设置开启"的引导（`x-apple.systempreferences:com.apple.Notifications-Settings.extension`） |
| 前台展示 | 必须实现 `willPresent` 返回 `[.banner, .sound]`，否则 App 在前台时通知**不显示**，用户会以为没提醒 |
| 内容隐私 | 设置项「通知里隐藏待办内容」→ 副标题显示"有 1 条待办到期"（待办标题常含公司/客户名） |

### 4.3 排程策略（这里有个硬限制）

**先把概念说清楚：这里的「pending」不是"长期占着系统资源"，而是"提前在系统里登记一个定时器"。**

本地通知的工作方式就是这样：App 不运行时没有进程能执行代码，所以"到点弹横幅"必须提前把请求交给系统。收到通知后系统自动移除，不会堆积。换句话说，**发一条横幅 = 提前登记一条请求，这是唯一路径，不是我们额外占用的东西。**

Apple 工程师在开发者论坛确认过：**每个 App 同时处于 pending 状态的请求上限是 64，无 API 可绕过**（[developer.apple.com/forums/thread/811171](https://developer.apple.com/forums/thread/811171)）。macOS 同样适用。

但你说得对——**日常用量根本碰不到这个数**。一个人未来 7 天内带具体时间的待办，通常就几条到十几条；把它当成"产品约束"是我上一版说重了。它真正的定位是**兜底机制**：极端情况（导入 500 条、批量建重复任务）下不要静默丢提醒。

调整后的策略（轻量版）：

| 规则 | 值 | 说明 |
|---|---|---|
| 排程窗口 | 未来 7 天 | 覆盖绝大多数真实使用；更远的到点前由启动/唤醒滚进来 |
| 数量上限 | 60 条（留余量） | 正常使用永远碰不到；超出时按 `due_at` 取最近的，其余滚动补排 |
| 全天任务 | 当天 09:00 提醒（可改） | 用户预期"早上看到今天要做的事" |
| 已过期未完成 | 启动时汇总 **1 条** | 不逐条轰炸 |
| 重建时机 | 启动 / 唤醒 / 增删改完成 / 时区变更 | 先 `removeAll` 再重排，保证不重复 |

> 如果哪天真的要做"每天重复提醒"或"提前 1 天 + 当天两次"，请求数会翻几倍，那时再考虑"滚动队列"（把超出 64 的排队，腾出空位就补上）。一期不需要。

### 4.4 幂等与去重

- identifier 用 `todo.<uuid>` 固定不变 → 重建时按 id 移除再添加，不会重复弹。
- 已完成的待办必须先移除对应通知，否则"完成了还提醒"。
- 用户点了「完成」动作 → 写库 → 移除通知 → 回写 `completed_at`。
- 用户点了「延后 1 小时」→ 不改 `due_at`，写 `snoozed_until`，重排一条时间触发通知。

### 4.5 通知交互

| 动作 | 行为 |
|---|---|
| 点通知本体 | 打开 App，定位到该条待办并高亮 |
| 「完成」 | 标记完成，收起通知，清单里打勾 |
| 「延后 1 小时」 | 重新排 1 小时后；连续延后 3 次自动改为「明天 9:00」 |
| 「延后到明天」 | 重排到次日设置的默认时间 |

### 4.6 数据模型补充

在 02 文档的 `todo` 表上补四列：

```sql
ALTER TABLE todo ADD COLUMN remind_at INTEGER;          -- 覆盖默认提醒时间，NULL = 用 due_at
ALTER TABLE todo ADD COLUMN reminder_enabled INTEGER NOT NULL DEFAULT 1;
ALTER TABLE todo ADD COLUMN snoozed_until INTEGER;
ALTER TABLE todo ADD COLUMN completed_at INTEGER;
```

`due_at` / `remind_at` 一律存 **epoch 秒（UTC）**，展示时按本地时区换算；`UNCalendarNotificationTrigger` 的 `DateComponents` 按系统时区解释，跨时区自动跟随，不用我们处理夏令时。

### 4.7 六个容易踩的坑

1. **非沙盒 App 也能用**，但必须**固定 bundle id + 稳定签名**；反复 ad-hoc 重签会让系统重置通知授权，测试期会以为"代码坏了"。
2. App 没注册到 LaunchServices（直接从 build 目录 `open`）时通知可能不弹。装到 `/Applications`，或 `lsregister -f` 刷一次。
3. `UNUserNotificationCenter.current().delegate` 要在 `applicationWillFinishLaunching` 里设好，晚于启动完成会漏掉首次回调。
4. macOS 上通知的 `UNNotificationAction` 需要显式 `registerCategories`，不注册按钮不显示。
5. 系统休眠期间到点的通知，唤醒后会补投——但**补投不保证顺序**，别依赖通知顺序做状态变更，一切以库里的 `due_at` 为准。
6. 测试时把系统时间往未来调，`UNCalendarNotificationTrigger` 会立刻触发一堆；测完记得清理 pending。

## 五、改造清单（文件级）

| 层 | 动作 | 预估 |
|---|---|---|
| `MouseHoldToTalkManager` | 新增 `commandTodoEnabled` 开关；`mouseDown` 时读 `modifierFlags`，`.askable` + ⌘ → 走待办回调（原 ask 分支保持不变） | 0.5 人日 |
| `AppDelegate` | 抽 `stopRecording(intent:)`，问 AI / 待办 / 听写共用录音与识别段，只在收尾分叉 | 1 人日 |
| `core/Todo` | `TodoExtractor`（结构化）、`TimeNormalizer`（时间校验）、`TodoValidator` | 3~4 人日 |
| `core/Storage` | SQLite 建表 + `TodoRepository`（CRUD、查询、幂等插入） | 2 人日 |
| `app/Features/Todo` | 清单、行、详情、编辑、搜索、撤销 Toast | 4~5 人日 |
| `app/Services/NotificationService` | 授权、排程重建、动作处理、降级 | 2~3 人日 |
| 设置页 | 「记待办」手势说明 + 提醒时间 + 通知隐私开关 | 1 人日 |

**合计约 14~17 人日**（比 02 文档的 14~19 人日多出提醒部分，因为原估算没算通知）。
